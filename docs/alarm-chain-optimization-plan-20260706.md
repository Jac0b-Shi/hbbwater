## 1. 当前告警链路基线

系统已形成两条告警链路：

| 链路 | 触发条件 | 数据输入 | 当前实现 | 主要文件 |
|---|---|---|---|---|
| **实时告警** | 超声波测距越阈值（`warning_level` / `danger_level`） | 单传感器读数 | `alerting.py` → `_handle_ultrasonic_alerts` | `backend/app/services/alerting.py` |
| **浸水检测** | 浸水传感器 `water_detected=true` | 单传感器 | `_handle_immersion_alerts` | 同上 |
| **预报告警** | 未来 N 小时降雨驱动的水位压力模型 | `RainfallForecastHourly` + 最新超声波读数 | `forecast_alerts.py` 的 `segmented_pressure_v1` | `backend/app/services/forecast_alerts.py` |
| **通知分发** | 邮件 + Webhook（含企业微信适配） | `Alert` + `Sensor` + `Reading` / `Prediction` | `dispatch_alert_notifications` | `backend/app/services/notifications.py` |

未提交变更中新增的 `forecast_alerts` 模块已具备：
- `forecast_alert_profiles`：按传感器配置预测窗口、阈值、泵参数
- `forecast_prediction_runs/results`：预测批次与结果台账
- 前端 `Alerts.vue` 双 Tab（实时 / 预报）
- 预报告警类型 `forecast_high_water` 已接入通知渠道

但仍为 **建议-only**（`NoopPumpController`），不执行真实泵控。

## 2. 深度报告核心约束（与告警链路直接相关）

### 2.1 雨量源优先级
- **主源**：`A5151` 宝山大场上大附中站
- **辅助源**：`58362` 宝山国家站仅用于区域背景、数据质量交叉核验、`A5151` 缺测时降级参考
- **禁止**：两站默认求均值、取最大值或等权融合

### 2.2 水位传感器标定与一致性
- 当前临时首次越堤线：`002≈81.2 cm`，`003≈70.6 cm`（声轴垂直假设，尚未完成姿态测量）
- 双传感器统计映射：`s003 ≈ 0.9840·s002 − 9.26`，残差中位数约 0.11 cm，95% 分位约 0.42 cm
- 在线一致性阈值建议：`|residual| > 1.5 cm` 连续 3 个周期 → 预警；`|residual| > 3.0 cm` 或突变 → 强异常候选

### 2.3 泵状态与水量平衡
- 泵数状态 `n_t ∈ {0,1,2,3}`，常态最多 2 台运行，极端可 3 台并行
- 两泵候选净降深 `q2 ≈ 6.23 cm/h`（5.9–6.4 cm/h 范围），单泵 `q1` 与三泵 `q3` 待标定
- 泮池实测面积 `A0 = 31,762 m²`，当前水面距首次越堤约 17 cm，对应调蓄体积约 5,400 m³

### 2.4 分级控制建议
| 级别 | 条件 | 动作 |
|---|---|---|
| L0 正常 | 水位安全、无显著上涨 | 全停，轮换首启泵 |
| L1 提前控制 | 进入启动线或雨强+上涨斜率预示即将越线 | 启动 1 台主泵 |
| L2 加强排水 | 单泵后仍上涨或预测入流超单泵能力 | 投入第 2 台泵 |
| L3 极端/应急 | 两泵仍不可控、接近越堤或极端短时雨强 | 投入第 3 台泵 |
| E0 | 越堤发生 | 全泵保持、最高级告警、现场封控 |

### 2.5 告警与故障安全原则
- 传感器不一致不得直接触发停泵；泵已运行应保持安全状态
- 单传感器孤立越线且另一点/斜率/雨量不支持 → 保持安全泵态 + 故障告警
- 连续 2–3 次越线或多源确认 → 全能力排水 + 人员应急处置

## 3. 关键差距分析

| 编号 | 差距项 | 当前状态 | 风险 |
|---|---|---|---|---|
| G1 | 雨量源未强制 A5151 优先 | `_select_station_id` 按 `role desc` 选第一个有预报数据的站 | 可能用 58362 驱动校园模型，导致误报/漏报 |
| G2 | 预报模型未校准 | `segmented_pressure_v1` 使用硬编码压力阈值，未结合 q2、A0、越堤裕度 | 预测误差大，无法支撑 L1/L2/L3 分级决策 |
| G3 | 无传感器一致性校验 | 实时告警和预报告警都只依赖单传感器 | 单点跳变/故障可能导致误告警或漏掉真实风险 |
| G4 | 无统一越堤裕度计算 | 系统仍使用 `warning_level/danger_level` 原始阈值，未换算到 17 cm 裕度 | 阈值可能过晚（如旧 70/60 cm 已属于严重淹没区） |
| G5 | 无泵状态台账 | `NoopPumpController` 只输出建议，无 0/1/2/3 状态识别和记录 | 无法验证分级控制策略，无法标定 q1/q2/q3 |
| G6 | 无 Shadow Mode / Auto Mode 区分 | 预报告警dry_run只是是否创建 Alert，无全局控制模式开关 | 自动化升级路径不清晰，存在误动作风险 |
| G7 | 通知渠道未按告警类型分流 | 预报告警和实时告警共用同一 webhook/邮件模板 | 值班人员难以区分“已发生”和“将发生”，信息密度不足 |
| G8 | 缺少数据质量标记传播 | 雨量缺测、传感器跳变、仿射残差超限未进入告警置信度 | 告警置信度不可解释，难以做降级策略 |

## 4. 优化目标

1. **数据可信**：建立 A5151 主源 + 58362 降级 + 双传感器一致性 + 跳变检测的输入质量门。
2. **模型可解释**：将预报模型从“分段压力阈值”升级为“基于越堤裕度、实测/预测雨强、泵效 q2 的水量平衡压力模型”。
3. **控制分级**：形成 L0–L3 泵控建议，支持 Shadow Mode（仅建议）与 Auto Mode（自动执行）两阶段切换。
4. **告警精准**：按风险等级、越堤预计时间、置信度生成差异化告警，减少误报与告警疲劳。
5. **通知分流**：实时告警、预报告警、传感器故障告警使用不同模板和升级策略。

## 5. 工作包与实施计划

### 阶段一：数据质量与输入层加固（2–3 周）

#### WP1.1 雨量源优先级与降级策略
- 在 `forecast_alerts.py` 中显式实现 `A5151` 优先选择逻辑
- 当 `A5151` 无预报/实况数据时，标记 `rain_source_degraded=true` 并降级到 `58362`
- 当两站同时缺测/异常时，禁用纯雨量预触发，仅保留水位阈值控制，并发出数据源异常告警
- 新增配置项：`forecast_primary_station=A5151`、`forecast_auxiliary_station=58362`、`fusion_mode=none`
- **文件**：`backend/app/services/forecast_alerts.py`、`backend/app/models.py`（新增 `ForecastAlertGlobalConfig` 或复用 `system_config`）

#### WP1.2 双传感器一致性在线校验
- 在数据入库或告警触发前，增加 `002→003` 仿射映射残差计算：`e_t = s003 − (0.9840·s002 − 9.26)`
- 引入动态容差：根据当前水位变化速度调整残差阈值
- 残差持续超限时：
  - 生成 `sensor_inconsistency` 类型告警（或作为 `details` 中 `quality_flag`）
  - 降低该传感器告警置信度
  - 单传感器越阈值但残差异常 → 不直接触发高水位告警，改为故障告警 + 人工核验
- **文件**：`backend/app/services/alerting.py`、新增 `backend/app/services/sensor_quality.py`

#### WP1.3 水位跳变与异常值检测
- 单步变化 `|Δs| > 3 cm` 标记为跳变候选
- 结合 002/003 一致性、雨量、泵状态进行跳变确认
- 跳变点前后 1–2 个采样周期屏蔽，避免插值污染和误告警
- **文件**：`backend/app/services/sensor_quality.py`

### 阶段二：预报模型重构（3–4 周）

#### WP2.1 统一水位裕度模型
- 以传感器原始读数计算“临时越堤裕度”：
  - `m002 = s002 − 81.2`
  - `m003 = s003 − 70.6`
- 完成物理标定后，替换为统一高程裕度 `H_t`
- 在 `Sensor` 模型中增加字段：`overflow_level_cm`、`overflow_confidence`（临时/已标定）
- **文件**：`backend/app/models.py`、`backend/app/schemas.py`

#### WP2.2 升级 `segmented_pressure_v1` → `water_balance_v1`
- 输入：A5151 实况/预报雨强、当前越堤裕度、双传感器平均/最小裕度、泵效参数
- 核心逻辑：
  - 自然上涨项：基于雨强和产流系数估算
  - 排水项：按当前泵状态 n_t 应用 `q_n`（默认 q2=6.23 cm/h，q1/q3 待标定）
  - 输出：未来各时刻越堤裕度、预计越堤时间 `T_overflow = H_t / v_rise`
- 引入 `lower_bound` 机制：暴雨事件下，即使模型输出偏低，也强制触发关注/预警
- **文件**：`backend/app/services/forecast_alerts.py`、新增 `backend/app/services/water_balance.py`

#### WP2.3 泵削峰模型校准入口
- 在 `ForecastAlertProfile` 中支持配置：
  - `pump_count`（0/1/2/3）
  - `pump_capacity_mm_per_min`（可逐台配置）
  - 默认使用报告推荐的 q2=6.23 cm/h → 对应 `pump_capacity_mm_per_min ≈ 1.04 mm/min`
- 模型输出同时给出：无泵上涨、当前泵态下上涨、全泵运行下上涨，用于 L1/L2/L3 决策
- **文件**：`backend/app/services/forecast_alerts.py`、`backend/app/services/pump_control.py`

### 阶段三：控制与告警策略升级（3–4 周）

#### WP3.1 泵状态反演与台账
- 在未安装 PLC 反馈前，基于以下规则反演历史/当前泵数 `n_t`：
  - 无泵时水位持平或上涨（排除跳变）→ n_t=0
  - 持续下降且变化点靠近整点/半点 → n_t≥1
  - 下降速率接近 q2 → n_t=2；接近 q1 → n_t=1；接近 q3 → n_t=3
- 新增模型/表：`PumpStateLog`（时间、传感器、推断泵数、置信度、依据）
- 为后续 `q1/q3` 标定提供数据
- **文件**：新增 `backend/app/services/pump_state_inference.py`、`backend/app/models.py`

#### WP3.2 分级控制建议（L0–L3）
- 扩展 `PumpControlContext` 与 `PumpController`：
  - 输入：当前裕度、预计越堤时间、A5151 雨强、当前泵态、可用泵数
  - 输出：`{level: L0/L1/L2/L3/E0, action: none/start_1/start_2/start_3, reason, executable}`
- `NoopPumpController` 继续用于 Shadow Mode
- 新增 `ShadowPumpController` 与 `PlcPumpController`（预留接口）用于未来切换
- **文件**：`backend/app/services/pump_control.py`

#### WP3.3 告警生命周期统一
- 统一实时告警与预报告警的冷却、升级、解除逻辑
- 实时告警：基于读数恢复自动解除
- 预报告警：基于风险等级下降自动解除（已有）
- 新增“置信度衰减”：当输入数据质量降级时，自动降低告警严重级别或切换为关注
- **文件**：`backend/app/services/alerting.py`、`backend/app/services/forecast_alerts.py`

### 阶段四：通知与前端优化（2–3 周）

#### WP4.1 通知模板分流
- 实时高水位：`alert.triggered` → 强调“已越线/正在发生”
- 预报高水位：`alert.forecast` → 强调“预计越堤时间、无泵/泵后上涨、建议动作”
- 传感器故障/不一致：`sensor.fault` → 单独模板，避免与高水位混淆
- 企业微信文本增加差异化标题和字段
- **文件**：`backend/app/services/notifications.py`、`backend/app/services/email.py`

#### WP4.2 前端告警中心统一
- 合并实时/预报告警视图，增加筛选：告警类型、风险等级、数据质量标记
- 在预报告警详情中展示：
  - 使用的雨量站（是否降级）
  - 双传感器一致性状态
  - 预计越堤时间线
  - 泵控建议（L0–L3）
- 在设置页增加：Shadow Mode / Auto Mode 开关、雨量源优先级、传感器一致性阈值
- **文件**：`frontend/src/views/Alerts.vue`、`frontend/src/views/Settings.vue`

### 阶段五：测试、验证与上线（2–3 周）

#### WP5.1 离线回放验证
- 使用导出 CSV（2026-05 至 2026-07）做历史事件回放
- 评估指标：
  - 误报率、漏报率
  - 预计越堤时间误差
  - 启停次数、总运行时间
  - 危险阈值以下暴露时长
- 方法：滚动起点验证 + 按降雨事件留一验证
- **文件**：新增 `backend/tests/test_forecast_alerts.py` 用例、新增 `scripts/forecast_backtest.py`

#### WP5.2 影子模式运行
- 部署后保持 `dry_run=false` 但 `pump_control_mode=shadow`，持续 2–4 周
- 记录每条控制建议与人工实际操作差异，校准 q1/q2/q3 和阈值
- **文件**：`backend/app/services/pump_control.py`、`backend/app/services/forecast_alerts.py`

#### WP5.3 工程化验收
- 对照深度报告和 GB 50014-2021 建议验收清单：
  - 三种控制方式（硬接线/就地/远程）

## 7. 建议的首期迭代（MVP）

为在 4–6 周内形成可用改进，建议首期完成：

1. **WP1.1 + WP1.2 + WP4.1**：先解决“输入不可信”和“通知不区分”两个最紧迫问题，降低误报率。
2. **WP2.1**：在传感器配置中增加越堤裕度字段，将现有 `warning_level/danger_level` 重命名为或补充为“越堤裕度”语义。
3. **WP2.2 最小版**：保留当前 `segmented_pressure_v1`，但引入 A5151 强制主源、双传感器最小裕度、暴雨事件下限，作为 `water_balance_v0.5` 上线 Shadow Mode。
4. **WP3.2 最小版**：在预报告警详情中输出 L0–L3 建议，但不执行任何真实控制。

这样可在不改变现有实时告警行为的前提下，显著提升预报告警的可信度和可解释性，并为暑期 PLC 改造提供数据基础。

## 8. 验收标准

| 维度 | 验收项 | 通过标准 |
|---|---|---|
| 数据质量 | A5151 主源策略 | 预报告警 `station_id=A5151` 占比 ≥ 95%；58362 触发时必有 `degraded` 标记 |

| 控制 | 分级建议 | 所有 warning/critical 预报告警附带 L1–L3 建议，且原因可解释 |
| 通知 | 分流效果 | 实时告警与预报告警在 Webhook/邮件中标题、字段可区分 |
| 安全 | Shadow Mode | 默认 `pump_control_mode=shadow`，任何自动执行需显式切换且记录审计日志 |

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| A5151 预报数据缺失或延迟 | 预报告警失效 | 实现降级到 58362 + 水位阈值保底 + 数据源异常告警 |
| 传感器姿态未最终标定 | 越堤裕度计算存在偏差 | 明确标注“临时阈值”，采用双传感器最小裕度保守策略 |
| q1/q2/q3 未标定 | 泵削峰模型误差大 | 默认使用报告 q2=6.23 cm/h，单泵/三泵参数通过影子模式迭代校准 |
| 告警升级过快导致告警疲劳 | 值班人员忽视 | 统一冷却策略、按置信度/风险等级分流、避免重复通知 |
| 自动化误动作 | 人员安全/设备损坏 | 必须保留硬接线/就地控制优先，Auto Mode 需人工审批和审计 |
